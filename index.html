🧐 AI 審 AI：Code Review Max 多開審查者，但盲點相同就沒用

📰 發生什麼、為什麼重要

Code Review Max 讓多個跨供應商模型的審查 agent 各自獨立看一遍，再由彙整 agent 合成一份審查，比 Lite、Balanced 慢、耗更多額度，價格未公開。Copilot 核准 GA 後可以計入必要核准數，但預設關閉、可限定路徑，新 push 會讓舊核准失效。AI 報提醒：審查 agent 若盲點相同，多開幾個也不見得更安全。

💡 我的見解（分析觀點）

我覺得「跨供應商」是這個設計的重點：同一個模型開三份，錯的地方多半也一樣。這和 10/25 Cloudflare 資安稽核的經驗一致，單輪只找到多輪總數的一半左右，所以要靠獨立的驗證者去推翻候選。另外，Max 更耗額度，等於審查也進了 10/29 的預算帳本。核准預設關閉、新 push 讓舊核准失效，這兩個預設我覺得很對：AI 核准應該是可以撤回的，而不是一次蓋章。

📚 學到什麼

冗餘要有效，前提是彼此獨立；多個相同的審查者只會重複同一個錯。

🧩 agent 工作流程變成技能：superpowers、JiTTesting 與「要人點頭」的自我改進

📰 發生什麼、為什麼重要

obra/superpowers 登上 GitHub 每日趨勢榜，把散落在 prompt 裡的經驗整理成可組合的技能模組；Cloudflare 的 security-audit-skill 也再度上榜（10/25 首見）。Meta 公布 JiTTesting 一年全公司部署成果：在工程師寫程式的當下用 LLM 生成測試，用 human-on-the-loop 設計避免誤判疲勞。Copilot Automations 則會觀察輸出被怎麼對待，提出修改自身 prompt、工具或觸發條件的提案，必須經人接受才生效。

💡 我的見解（分析觀點）

我覺得開發者文化正在從「寫好提示詞」轉向「共享工作流程」：一套技能可以被別人直接拿去用，行為也比較可預測。10/29 Smarsh 把 AWS 架構審查寫成 Claude skill，也是同一件事。我注意到這三則都刻意把人留在迴路裡：JiTTesting 讓工程師保有最終判斷，Automations 的自我修改要人點頭。這對我自己的流程也適用，技能化之後更要清楚哪一步由人否決。

📚 學到什麼

把重複的工作流程寫成技能，比每次重寫提示詞更穩；但能自我修改的流程，改動一定要有人審。

💡 我的見解（分析觀點）

這張卡和我的工作最相關。我覺得重點不在快 14.7 倍，而是承認「優化器拚命壓的那個數字」和真正要的結果之間有落差，於是換一個更貼近真實的可微分指標。AI 優化器越強，越會鑽代理指標的漏洞，所以和 i1 一樣，最後還是要看繞線後的真實結果。

📚 學到什麼

古德哈特定律：指標一旦變成目標，就不再是好指標；解法是換更貼近真實的指標，並定期用真實結果校準。
